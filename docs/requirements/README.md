## このドキュメントについて

### 目的
マイクロサービスの**ビジネス要件**を明確にし、開発者・PM・ビジネス担当者が共通認識を持つため。

### 要件定義ファイルの構成
各サービスのMarkdownファイルには以下が記載されています：
- **サービス概要**: 責務と主な役割
- **機能要件**: 詳細な機能仕様

**注意**: 実装詳細（API設計、DB設計、技術スタック等）は含まれていません。
技術的な内容は [プロジェクトルートのREADME](../../README.md) を参照してください。

## 実装優先順位

### Phase 1: 基盤サービス（Week 1-2）⭐⭐⭐
**必須**: 全サービスの前提となる基盤

| サービス | 概要 | 重要度 |
|---------|------|--------|
| [Auth Service](./01_auth_service.md) | 認証・認可・JWT発行 | **必須** |
| [Shop Service](./02_shop_service.md) | ショップ・商品管理 | **必須** |

**なぜこの順序？**
- Auth Service: すべてのサービスがJWT検証に依存
- Shop Service: 商品データがないとビジネスが成立しない

---

### Phase 2: コアビジネス機能（Week 3-5）⭐⭐
**最優先**: ビジネスの中核（購入フロー）

| サービス | 概要 | 重要度 |
|---------|------|--------|
| [Customer Service](./03_customer_service.md) | カスタマー体験・カート | **高** |
| [Inventory Service](./04_inventory_service.md) | 在庫管理・引き当て | **高** |
| [Order Service](./05_order_service.md) | 注文処理・Saga | **高** |
| [Payment Service](./06_payment_service.md) | 決済処理・Stripe連携 | **高** |

**なぜこの順序？**
- Customer → Inventory → Order → Payment の順で依存関係があるため

---

### Phase 3: 拡張機能（Week 6-8）⭐
**重要**: ユーザー体験の向上

| サービス | 概要 | 重要度 |
|---------|------|--------|
| [Shipping Service](./07_shipping_service.md) | 配送管理・追跡 | 中 |
| [Notification Service](./09_notification_service.md) | メール・プッシュ通知 | 中 |
| [Review Service](./10_review_service.md) | レビュー投稿・評価 | 中 |
| [Search Service](./11_search_service.md) | 商品検索・Elasticsearch | 中 |

---

### Phase 4: サポート機能（Week 9-10）
**補助**: あると便利だが必須ではない

| サービス | 概要 | 重要度 |

## サービス依存関係

### 依存関係図

```
                    Auth Service（基盤）
                          ↓
    ┌─────────────────────┼─────────────────────┐
    ↓                     ↓                     ↓
┌─────────┐         ┌──────────┐         ┌──────────┐
│  Shop   │←────────│ Customer │         │  Admin   │
│ Service │         │ Service  │         │ Service  │
└─────────┘         └──────────┘         └──────────┘
    ↓                     ↓
┌─────────┐         ┌──────────┐
│Inventory│         │  Order   │
│ Service │←────────│ Service  │
└─────────┘         └──────────┘
                          ↓
                    ┌──────────┐
                    │ Payment  │
                    │ Service  │
                    └──────────┘
                          ↓
                    ┌──────────┐
                    │Notifica- │
                    │  tion    │
                    └──────────┘
```

### 依存関係の説明

- **Auth Service**: すべてのサービスが依存（JWT検証）
- **Shop Service**: Customer, Search, Reviewが商品情報を参照
- **Inventory Service**: Order Serviceが在庫引き当てで依存
- **Order Service**: Payment, Shipping, Notificationが注文情報を参照
- **Payment Service**: 決済完了後に複数サービスへイベント発行
- **Notification Service**: 各サービスからのイベントを購読

## 主要なユースケース

### 1. 商品購入フロー

```
[Customer Service]
    ↓ カートに追加
[Inventory Service] ← 在庫確認
    ↓ 在庫引き当て
[Order Service] ← 注文作成
    ↓ 決済処理開始
[Payment Service] ← Stripe決済
    ↓ 決済成功
[Notification Service] ← 注文確認メール送信
```

**シーケンス**:
1. カスタマーがカートに商品を追加
2. 注文確定時、Inventory Serviceで在庫を引き当て
3. Order Serviceが注文を作成
4. Payment Serviceで決済処理
5. 決済成功後、Notification Serviceがメール送信

---

### 2. ショップ開設フロー

```
[Auth Service]
    ↓ ショップ運営者として登録
[Shop Service]
    ↓ ショップ情報登録
[Admin Service] ← 承認待ち通知
    ↓ 管理者が承認
[Search Service] ← 検索インデックス更新
    ↓ ショップ公開
```

**シーケンス**:
1. ショップ運営者がAuth Serviceで登録
2. Shop Serviceでショップ情報を登録
3. Admin Serviceに承認待ち通知
4. 管理者が承認すると、Search Serviceに反映
5. 検索可能になる

---

### 3. 商品検索フロー

```
[Customer Service]
    ↓ 検索クエリ
[Search Service] ← Elasticsearch検索
    ↓ 商品ID一覧
[Shop Service] ← 商品詳細取得
    ↓ 在庫数確認
[Inventory Service]
```

**シーケンス**:
1. カスタマーが商品を検索
2. Search ServiceがElasticsearchで検索
3. Shop Serviceで商品詳細を取得
4. Inventory Serviceで在庫数を確認
5. 結果を返す

## 共通ビジネスルール

### 認証・認可
- すべてのサービスは **Auth Service の JWT 検証**を使用
- **ロール**: `customer`, `shop_owner`, `admin`
- 各APIエンドポイントに必要な権限を定義
- 権限不足: `403 Forbidden`
- 未ログイン: `401 Unauthorized`

### データ管理
- 各マイクロサービスは**独立したデータベース**を持つ
- サービス間のデータ参照は **gRPC 経由**で行う
- データの整合性は **Saga パターン**で管理
- イベントソーシングによる状態変更の記録

### エラーハンドリング
- gRPC ステータスコードを使用
- ビジネスエラー: 詳細なエラーメッセージを返す
- システムエラー: ログに記録し、ユーザーには汎用メッセージ
- リトライ可能なエラーは明示的に示す

### トランザクション管理
- 単一サービス内: データベーストランザクション
- サービス間: Saga パターンによる分散トランザクション
- 補償トランザクション: 失敗時のロールバック処理

## 用語集

| 用語 | 説明 |
|------|------|
| **ショップ** | 商品を販売する店舗。1つのショップ運営者が複数管理可能 |
| **カスタマー** | 商品を購入するエンドユーザー |
| **ショップ運営者** | ショップを管理し、商品を出品・販売するユーザー |
| **管理者** | システム全体を管理するユーザー（ショップ承認、ユーザー管理など） |
| **在庫引き当て** | 注文時に在庫を仮確保すること。決済完了で確定、失敗でリリース |
| **Saga パターン** | 分散トランザクションを管理する設計パターン |
| **補償トランザクション** | 分散トランザクション失敗時のロールバック処理 |
| **バリエーション** | 商品の属性（サイズ、色など）ごとの在庫・価格管理 |
| **イベント駆動** | サービス間の連携をRabbitMQのイベントで行うアーキテクチャ |
| **JWT** | JSON Web Token。認証トークンの形式 |
| **RBAC** | Role-Based Access Control。ロールベースアクセス制御 |
